# My Daily — Personal Finance Tracker

React 19 SPA (TanStack Router, file-based) for tracking income/expenses/categories, with AI-assisted receipt parsing. No backend lives in this repo — all data comes from a REST API at `VITE_BASE_URL`; this app is the client only.

## Architecture (WHAT)

- **Routing**: `src/routes/**` — TanStack Router file-based routes, kept thin. Each route file just wires a path to a page component, e.g. `src/routes/expense/index.ts` → `src/pages/expense/ExpensePage.tsx`. `src/routeTree.gen.ts` is generated by the router Vite plugin — never hand-edit it.
- **Feature module pattern** — every entity under `src/pages/<feature>/` (category, expense, income, report, dashboard, profile, login) follows the same shape. Use `src/pages/category/` as the reference:
  - `<Feature>Page.tsx` — page component, composes hooks + shared components
  - `<feature>.service.ts` — API calls, one Effect per endpoint (see `src/pages/category/category.service.ts:8`)
  - `<feature>.type.ts` — request/response types for that feature
  - `<feature>.schema.tsx` — form validation schema, where forms exist
  - `hooks/use<Feature>Page.ts` — page-level state/orchestration hook; owns local state, calls `.service.ts` functions via `runEffectSafe`, and is the only thing the page component talks to (see `src/pages/dashboard/hooks/useDashboardPage.ts`)
- **Shared UI**: `src/components/{DataTable,Filter,Form,Layout,Loading,PageContainer,Popup}` — reuse these instead of building one-off equivalents. `Layout.tsx` picks between `AuthLayout.tsx` and `MainLayout.tsx`.
- **Shared types**: `src/types/common.ts` defines `CommonResponseList<T>`, `CommonResponse<T>`, `CommonParams`, `CommonOptions` — the envelope shapes the API returns. New service functions should type their return against these, not ad-hoc shapes.
- **State**: local/page state lives in the page's `use<Feature>Page.ts` hook. Only cross-cutting global state goes in `src/store/*.store.ts` (zustand) — currently just loading-overlay state (`useBlockLoading.store.ts`).

## Effect-TS HTTP layer (WHY + HOW)

All API calls go through `src/lib/http.ts`, not raw `fetch`. It wraps `@effect/platform`'s `HttpClient`:

- `http.get/post/put/delete` return `Effect.Effect<T, HttpError, HttpClient.HttpClient>` — write service functions in that shape (see `category.service.ts` for the pattern).
- `HttpError = HttpResponseError | HttpNetworkError` (`src/lib/http.ts:35`) — typed failures, not thrown exceptions. Handle both cases rather than wrapping calls in try/catch.
- A `401` response clears the stored session and hard-redirects to `/login` inside `http.ts` itself (`src/lib/http.ts:75`) — this is global behavior, not something individual callers need to (or should) replicate.
- To actually run an Effect from a component/hook, use `runEffect` or `runEffectSafe` from `src/lib/runtime.ts`, not `Effect.runPromise` directly — they thread the app's `ManagedRuntime`/layers. `runEffectSafe` is preferred in hooks since it returns `{ success, data }` / `{ success, error }` instead of throwing.
- Auth token is read from `localStorage` (`src/utils/localstorage.ts`) and attached as `Authorization: Bearer <token>` automatically by `http.ts` — don't pass it manually per-call.

## AI receipt parsing

`src/hooks/useAi.ts` calls the Google GenAI SDK (`gemini-2.5-flash`) **directly from the browser** using `VITE_GEMINI_API_KEY`, not through the backend API. The extraction prompt lives in `src/pages/expense/expense.md.ts`. Because the key is `VITE_`-prefixed it ships in the client bundle — this is an existing, known constraint of the current design, not an oversight to silently "fix" mid-task; flag it explicitly if a change would make the exposure worse (e.g. widening its scope) rather than reworking the auth model unprompted.

## Commands (HOW)

| Command | Effect |
|---|---|
| `npm run dev` | Starts `src/index.ts` — Express + Vite in middleware mode, **SPA app type**, not SSR |
| `npm run build` | `vite build` — static client bundle to `dist/` |
| `npm run preview` | Serve the production build locally |
| `npm run lint` | ESLint over the whole repo — run after any change, it's the only formatting/style gate (no Prettier config, no style rules to hand-enforce) |

There is no test suite in this repo (no test runner in `package.json`) — don't assume `npm test` exists or invent test files unless asked to add testing infrastructure.

`entry-server.tsx` / `entry-client.tsx` exist and imply SSR, but `src/index.ts` boots Vite with `appType: 'spa'`, and both `Dockerfile` and `vercel.json` serve/rewrite everything to a static `index.html`. Treat this as a client-rendered SPA in practice; don't assume `entry-server.tsx`'s `render()` is actually invoked anywhere.

## Environment

Required vars (see `.env.example`): `NODE_ENV`, `VITE_BASE_URL` (backend API origin), `PORT`, `VITE_GEMINI_API_KEY`. All `VITE_*` vars are public in the client bundle — never put a secret that must stay server-side behind a `VITE_` prefix.
